# ReplayScope portfolio walkthrough

Use these steps to demonstrate the *working application* and its engineering tradeoffs during a Flask/backend interview. The datasets are **synthetic fixtures generated by source code**, not external benchmarks or a live trained agent.

## 1. Prepare the demo

From an activated Python virtual environment in the project folder:

```powershell
py -m pip install -e ".[dev]"
py -m flask --app replayscope:create_app seed-demo --dry-run
py -m flask --app replayscope:create_app seed-demo
py -m flask --app replayscope:create_app run --debug
```

`--dry-run` lists the planned imports without writing experiment, upload or run records. The regular command inserts exactly two experiments *if they are absent* and imports the deterministic JSON bytes. It reuses identical existing source data. No existing experiment, upload or run is deleted.

If you already use a SQLite database, your workspaces stay available. The demo names start with **SYNTHETIC DEMO** so they cannot be mistaken for authentic benchmark results.

## 2. Explore the navigation example

Find **SYNTHETIC DEMO — Navigation Trials**.

- Agent: `Navigator`.
- Versions: `baseline`, `candidate`.
- Scenarios: `maze-easy`, `maze-medium`, `maze-hard`.
- Seeds: integers 1–16 shared between versions for each scenario.
- Records: **96** in one uploaded dataset.
- Outcomes: `success` / `failure`; optional `timeout` or `blocked_path` failure labels.
- Metadata identifies every row as synthetic; trace events include start, checkpoint and finish.

Use the scenario filter. Explain that success percentages, duration averages and numerical scores are descriptive and not a controlled causal experiment.

Open **Paired comparison**. You should see **48 unique matched scenario/seed pairs** and no ambiguous keys. Show the signed score differences and the coverage/exclusions panel. Explain why matching seeds is more honest than comparing unmatched aggregate scores, while still **not proving statistical significance**.

## 3. Explore the arena example

Open **SYNTHETIC DEMO — Arena Trials**.

- Agent: `ArenaBot`, with baseline and candidate versions.
- Scenarios: `arena-small`, `arena-large`.
- Seeds: 1–12 for each version and scenario.
- Records: **48**.
- Outcomes: `win`, `loss`, `draw` rather than task success/failure.
- Metadata and typed events are synthetic.

This demonstrates why the API does not conflate game win rate and task success rate.

## 4. Demonstrate backend engineering

Visit **API reference** at `/docs` and open `/api/v1/openapi.json`.

Explain the lifecycle:

1. Flask validates a JSON/CSV payload without coupling the parser to a game.
2. Uploads are deduplicated by SHA-256 within an experiment and stored under generated disk filenames.
3. Processing persists normalized runs and agent-version records.
4. SQLite + inline processing make the demo zero-dependency; Redis/RQ + PostgreSQL have dedicated integration tests in CI.
5. Read APIs aggregate by version/scenario; the comparison API pairs only unique matching keys.
6. Optional protected mode demonstrates session login, browser CSRF and separate bearer credentials for automation.

Sample datasets are **not** a benchmark performance claim. The more valuable portfolio evidence is architecture, reproducibility, error handling, tests and reasonable tradeoffs.

## 5. Interview questions to be prepared for

- Why Flask and server-rendered Jinja instead of a split frontend service?
- Why validate inputs before storing them, then parse them again in the worker?
- What is the purpose of content hashes and idempotent imports?
- What happens if an RQ worker crashes while processing an upload?
- When does SQLite cease to be a good choice, and how would you migrate to PostgreSQL?
- Why does matching scenario and seed not automatically establish causality?
- What would need to change before the application could be made public?

Be open about incomplete features. Worker retries, leases and concurrency regression tests exist, but transactional queue-outbox guarantees, production alerting, multi-user accounts and public hosting are not finished.
